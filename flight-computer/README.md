# PSI AVIONICS 2026 — Portenta H7 듀얼코어 로켓 에비오닉스

> **Repository migration, 2026-09-17:** imported the August 8 package.
> ST STM32 19.5.0 and Arduino Mbed 4.5.0 are pinned. After the five-second
> deployment lockout, velocity that remains unusable for **1000 ms continuously**
> now permanently disables its primary path, allowing the healthy IMU tilt
> backup. A usable sample resets this timer; isolated gaps retain the existing
> 500 ms recovery blanking. SD replay now decodes the health-note tokens.
> See [migration, tests, and legacy recovery](../docs/MIGRATION-2026.md).

Arduino Portenta H7(STM32H747)의 두 코어를 나눠 쓰는 로켓 비행 컴퓨터 펌웨어.

| 코어 | 파일 | 역할 |
|------|------|------|
| **M7** (480MHz) | `src/m7/main_m7.cpp` | 비행제어 전부: GNSS/IMU/바로미터 → UKF 칼만필터 → 상태머신(발사/정점/낙하산) → 서보. **100Hz 고정 루프**(절대 마감시각 스케줄링). 매 루프 데이터를 RPC로 M4에 전송 |
| **M4** (240MHz) | `src/m4/main_m4.cpp` | RPC 수신 → ① SD카드에 100Hz 전량 기록 ② XBEE로 25Hz 텔레메트리 송신 |

M7↔M4 통신은 RPC 스트림(`shared/ipc_protocol.h`). XBEE와 SD는 M4 전용이라
블로킹 I/O가 비행 루프를 방해하지 않는다. (RPC 왕복·M4의 XBEE 구동·SD 100Hz
무손실 기록 모두 하드웨어 검증 완료.)

> **소스에 주석이 거의 없는 이유**: 코드 설명은 전부 이 문서의
> [6. 코드 이해하기](#6-코드-이해하기)에 모아뒀다. 코드를 고치기 전에 그 장을 읽을 것.
> 소스에 남은 `// !` 표시는 "지우면 사고 나는 줄"이라는 뜻이며, 각각 6장에 근거가 있다.

## 준비물

- VS Code + PlatformIO 확장 (또는 `pio` CLI). 처음 빌드하면 툴체인/프레임워크 자동 설치.
- dfu-util (PlatformIO가 자동 설치): `~/.platformio/packages/tool-dfuutil-arduino/dfu-util.exe`

## 1. 빌드

```bash
pio run
```

두 env(M7/M4)가 모두 빌드된다. 결과물:
- `.pio/build/portenta_h7_m4/firmware.bin`
- `.pio/build/portenta_h7_m7/firmware.bin`

## 2. 업로드 — ★반드시 M4 먼저, M7 나중

M7의 `RPC.begin()`이 M4를 부팅시키므로 **M4 → M7 순서가 필수**다.
Flash 오프셋: M7=`0x08040000`, M4=`0x08100000` (변경 금지).

### 방법 A — PlatformIO 자동 업로드 (먼저 시도)

```bash
pio run -e portenta_h7_m4 -t upload
```
```bash
pio run -e portenta_h7_m7 -t upload
```

### 방법 B — dfu-util 직접 (방법 A가 `Cannot configure port / PermissionError` 로 실패할 때)

1. **DFU 모드 진입** — 둘 중 하나:
   - 보드 RESET 버튼 **더블탭** → 초록 LED가 숨쉬기 점멸하면 DFU 모드
   - 또는 1200bps 터치(PowerShell, COM5는 실제 포트로 교체):
     ```powershell
     $p=New-Object System.IO.Ports.SerialPort COM5,1200;$p.Open();Start-Sleep -m 150;$p.Close()
     ```
2. **확인**: `dfu-util -l` 출력에 `2341:035b`가 보이면 준비 완료.
3. **M4 먼저 플래시**:
   ```bash
   dfu-util -d 0x2341:0x035b -a 0 -s 0x08100000 -D .pio/build/portenta_h7_m4/firmware.bin
   ```
4. **M7 플래시** (`:leave`가 리셋→실행까지 수행):
   ```bash
   dfu-util -d 0x2341:0x035b -a 0 -s 0x08040000:leave -D .pio/build/portenta_h7_m7/firmware.bin
   ```

주의: `firmware.bin`이 없다는 에러가 나면 먼저 `pio run`으로 빌드할 것.

## 3. 부팅 확인

```bash
pio device monitor -b 115200
```

- 포트 번호는 플래시/리셋 후 바뀔 수 있다(COM5↔COM8↔COM10 관찰됨).
  장치관리자에서 USB PID **025B**(Portenta 앱모드)를 찾으면 된다.
- 부팅 로그를 처음부터 보려면 **모니터를 먼저 열어놓고 RESET**을 누를 것.
- 정상 부팅 순서: `[INIT] HELLO_GROUND` → `[TEST]` 서보 → `[CAL]`/`[ZERO]` IMU →
  `[ZERO]` 바로미터 기준기압 → `[STATE] PRELAUNCH` (총 ~37초).
- ⚠️ **보드의 빨간 LED가 계속 점멸하면 = RPC 실패(M4 미부팅)**. 이때 M7은 부팅을
  **진행하지 않고 그 자리에 멈춘다**(무한 점멸). SD 기록도 XBEE 텔레메트리도 전혀
  안 되는 상태라 의도적으로 막아둔 것이다. M4부터 재플래시할 것(순서 M4 → M7).
  노트북 없이 패드에서 판별하려고 만든 신호라, 정상 부팅에서는 LED가 켜지지 않는다.
- 최초 1회 부팅 시 옵션바이트 정리로 보드가 스스로 리셋해 45초쯤 무음일 수 있음(정상).

⚠️ **벤치 테스트 주의**: 센서를 흔들면 발사 판정(가속도>2g 등)이 넘어가
LAUNCH → 약 14초 후 DEPLOY(서보 작동)까지 자동 진행될 수 있다.
서보에 낙하산이 물려 있으면 주의.

## 4. 지상국 (XBEE 수신)

- 수신측 XBEE를 PC에 꽂고 지상국 프로그램(`ground-station/Groundstation.py`) 실행 — 별도 저장소/폴더.
- 출력 포맷:
  - 데이터: `[0x7E][PackedSensorData 90B][0x0A]` — 상태 1B + float 22개(마지막 = **gnss_alt**) + **health 1B**
  - 로그: `[0xAA]텍스트\r\n` — 캘리 진행상황, 에러 등
  - `[SYS] flight summary: written=N sd_drops=N log_drops=N ipc_bad=N fmt_drops=N` —
    착지(LANDED) 시 1회. `ipc_bad`는 체크섬 불일치로 버린 코어간 프레임 수(비행 중 처음
    발생 시 `[WARN] IPC frame rejected`가 즉시 1회), `fmt_drops`는 CSV 한 줄이 너무
    길어(UKF가 거대 값으로 발산하는 경우 등) 기록에서 빠진 레코드 수. 전부 0이 정상.

⚠️ **프레임 변경 이력**: health 바이트(07-30, 85→86B), **gnss_alt float(08-04, 86→90B)**.
현재 파서 포맷은 **`'<B' + 'f'*22 + 'B'`** (`Groundstation.py`는 반영 완료,
`Groundstation_MAC.py`/`Groundstation_test.py`/`monitor_rate.py`는 **여전히 85B 시절이라 미동작**)


**health 바이트 = 그 프레임 데이터의 유효기간 표시** (비트가 1이면 정상, `0xFF`=전부 정상):

| 비트 | 이름 | 의미 |
|------|------|------|
| 0x01 | IMU_FRESH | IMU 값이 30ms 이내 (제어에 쓸 수 있는 신선도) |
| 0x02 | BARO_FRESH | 기압 값이 60ms 이내 |
| 0x04 | IMU_ALIVE | IMU가 500ms 내 수신 (사망 판정 기준) |
| 0x08 | BARO_ALIVE | 기압계가 500ms 내 수신 |
| 0x10 | GNSS_ALIVE | 유효 UBX 프레임이 1s 내 수신 |
| 0x20 | BARO_REF | 기준기압이 품질검사 통과 = 고도 발사경로 활성 |
| 0x40 | VZ_TRUSTED | kalman vz 전개경로 유효(기준기압 품질 미달·cadence 불합격·비행 중 기압 공백·비행 중 IMU 사망 → 영구 해제) |
| 0x80 | VZ_USABLE | **지금 이 순간 vz 투표가 실제로 열려 있음** = trusted + cadence OK + **IMU 신선(30ms)** + 기압 신선 + `isfinite(kf_vel)` + 블랭킹 해제. 제어가 쓰는 `vzUsableNow()`와 **같은 함수**라 어긋날 수 없다 |

`FRESH=0 & ALIVE=1`이 **"값은 찍혀 있지만 낡은 값"** 구간이다 — 이때 비행로직은
그 값을 상태전이 판단에서 제외한다(동결값 재투표 차단, [6.4](#64-신선도의-두-등급)).

- 송신 속도는 기본 **25Hz** (`TELEM_DECIMATE=4`. 이 XBee3 Zigbee 링크에서 실측 무손실.
  50Hz 이상은 CTS 흐름제어 미결선으로 대량 유실됨).
  변경: `src/m4/main_m4.cpp`의 `TELEM_DECIMATE` 한 줄 (1=100Hz, 2=50Hz, 4=25Hz, 5=20Hz).

## 5. SD 비행 로그

부팅할 때마다 새 세션 파일을 만들고 **기존 파일은 절대 덮어쓰지 않는다**:

- `/fs/flight_NNN.csv` — 비행데이터 100Hz 전량. 첫 줄이 컬럼명이라 엑셀/메모장에서 바로 열림
- `/fs/flight_NNN.txt` — 캘리/이벤트 로그. **줄머리 `[숫자]`는 M7 미션 ms** — CSV
  `time_ms`와 같은 축이라 `[37412] [STATE] LAUNCH` ↔ CSV `time_ms=37412` 행으로
  변환 없이 바로 대조된다(구버전은 M4 수신 시각이라 +40초 오프셋 + 코어 간 틱 편차
  ~2.4%를 곱해야 했다). 셋업 구간은 미션 시계 시작 전이라 M7 부팅 ms로 찍히고,
  경계에 `[ZERO] mission clock start (boot +NNNNNms)` 한 줄이 남는다. M4가 스스로
  만드는 줄(부팅 SD 상태, IPC 경고, 비행 요약)만 `[M4 ms]` 접두로 구분된다.
  바로미터 기준기압 측정의 원샘플 `[BARO]` ~300줄은 **여기에만** 있다(XBEE로는 안 감).

CSV 마지막 컬럼 `note` = health 바이트를 사람이 읽는 말로 푼 **비고란**(행별 데이터 유효성):

| note 값 | 뜻 |
|---------|-----|
| `ok` | 그 행의 모든 센서값이 신선함 |
| (`gnss_alt` 컬럼) | note 바로 앞의 신규 컬럼(08-04). GNSS 해수면고도 m — **기록·회수 전용, 어떤 판정에도 미사용**. hAcc 게이트 통과 전엔 0.0 유지 |
| `imu_stale` / `baro_stale` | 값은 있으나 유효기간 초과(IMU 30ms/기압 60ms) — 상태전이 판단에서 제외됨 |
| `imu_dead` / `baro_dead` / `gnss_dead` | 500ms(GNSS는 1s) 무응답 = 센서 사망 판정 |
| `no_baro_ref` | 기준기압 미설정/품질미달 → 고도 발사경로 비활성 |
| `vz_off` | kalman vz 전개경로 **영구** 해제 — 기준기압 품질 미달, 비행 중 기압 공백, cadence 불합격(초기·드리프트), 또는 **비행 중 IMU 사망**(500ms) |
| `vz_settle` | vz 경로는 살아 있으나 그 행에서만 투표가 막힌 **임시** 상태 — cadence 무장 전(부팅 첫 ~2초), 공백 직후 500ms 블랭킹, IMU/기압 stale, `kf_vel` 비유한값/\|200\| 초과 |

여러 개면 `imu_stale\|baro_dead` 처럼 `|`로 이어진다. **정상 비행이면 전 구간 `ok`**이므로
사후분석에서 `note != ok` 행만 필터하면 센서 이상 구간이 바로 나온다.

200ms마다 fsync로 커밋하므로 **급단 시점까지 커밋된 내용은 온전**하다(하드웨어 검증 완료).
단 exactly-once 기록은 보장하지 않는다 — 아래 두 경우가 가능하다:

- **CSV 중복행**: fwrite는 성공했는데 fflush/fsync가 실패하면 같은 배치를 다음 주기에
  재기록한다. 유실보다 중복이 안전하다는 판단(의도된 동작). 사후분석에서 `time_ms`가
  같은 행이 연속으로 보이면 이 경우이므로 dedup 후 쓸 것.
- **txt 로그 유실**: 로그는 링버퍼에서 pop한 뒤 쓰므로, 그 직후 쓰기가 실패하면 해당
  줄은 복구되지 않는다.

연속 3회 실패하면 SD를 닫고(기록분 보호) XBEE만 계속 동작한다. SD 마운트 실패 시에도
SD만 끄고 XBEE는 정상. 오래된 세션 파일은 PC에서 수동 삭제.

# 6. 코드 이해하기

소스의 설명은 전부 이 장에 있다. 코드에는 구조를 나누는 배너와, 지우면 사고가 나는
자리에 붙인 `// !` 한 줄만 남겨뒀다.

**소스 안에서 길찾기**: 각 소스 파일 머리에 `[File map]` 목차가 있고, 본문의 섹션
배너에 같은 `[N]` 번호가 붙어 있다(M7은 [1]~[15], M4는 [1]~[6]). 파일 중간 어디서든
위로 스크롤해 가장 가까운 배너 번호를 보면 현재 위치를 알 수 있고, `[11]`처럼 번호로
검색하면 바로 점프된다. 함수 정의 순서는 "의존성 순서"(도구가 먼저, setup/loop가
마지막)로 고정 — C++의 선언-후-사용 규칙 때문이며 재배치하지 말 것.

## 6.1 실행 구조

**M7 — 비행 로직은 단일 흐름 + 출력 전담 TX 스레드 하나.** `loop()`(main 스레드)가
파싱 → UKF → 헬스 → 판정 → 서보를 순서대로 하고, 텔레메트리·로그는 **링에 push만**
한 뒤(µs, 항상 즉시 리턴) **절대 마감시각**(`Kernel::Clock::now() + 10ms`)까지 잔다.
블로킹 `RPC.write`는 BelowNormal 우선순위의 `txThread`가 전담한다 — M4의 SD 라이터와
같은 검증된 생산자-우선 패턴. **비행 상태(FSM·투표창·센서값)는 여전히 loop만 만진다**;
스레드와 공유하는 건 완성된 바이트 프레임이 담긴 SPSC 링 하나뿐이다.

```
parseGNSS → parseIMU → (새 기압샘플이면) parseBaro → parseKalman
          → updateSensorHealth → runDecision(FSM+서보)
          → health 바이트 스탬프 → ipcSendData → flushEvents
          → cadence 감시 → sleep_until(다음 마감)
```

**불변조건: 비행 루프에는 블로킹 RPC가 아예 없다.** `ipcSend`는 링 push뿐이라 M4가
완전히 죽어도 루프는 계속 돈다 — 링이 차면 프레임을 버리고 `dropped=` 카운트로 보고
한다(**제어 지속 > 기록 무손실**). USB 로그 출력도 txThread가 프레임 송신 시 함께
수행하므로 **비행 루프는 RPC·USB를 통틀어 IO를 전혀 하지 않는다**(센서 읽기 제외 —
I²C는 프리빌트 mbed라 타임아웃을 보장 못 하며, SDA 고착 벤치가 검증 수단이다).
판정 전 단계(파싱·헬스)의 경고는 여기에 더해 `logEvent()` 큐로 이연되어
`flushEvents()`(runDecision 이후)에서 발행된다. 루프는 자체 worst-case 작업시간과
데드라인 스킵을 계측해 `[WARN] loop max ...`로 보고한다. `[STATE]` 로그는 서보·상태 변경이라는 안전
동작 **뒤**라 즉시 발행.

상대 sleep이 아니라 절대 마감을 쓰는 이유: `millis()` 절삭과 작업시간 오차가
누적돼 실측 ~109Hz가 나왔었다. 마감을 넘기면 밀린 마감은 **건너뛴다**(따라잡기
버스트 금지 — 10ms 격자 위상 유지).

**M4 — 메인 루프 + SD 쓰기 스레드.**

| | 우선순위 | 하는 일 |
|---|---|---|
| `loop()` | Normal | RPC 바이트 수신 상태머신 → 링버퍼 push, XBEE 송신, 일회성 보고 |
| `sdWriter` | **BelowNormal** | 링버퍼 → CSV 변환 → 200ms마다 fwrite+fflush+fsync |

메인이 항상 라이터를 선점하므로 **SD 쓰기가 블로킹되는 동안에도 RPC 수신이
계속된다** = 무손실. 이 우선순위 관계가 무손실의 핵심이라 뒤집으면 안 된다.

## 6.2 데이터 흐름

```
[IMU]  UART 100Hz ─┐
[GNSS] UART  1Hz ──┼→ M7 loop → SensorData d → UKF(50Hz) → FSM → 서보(D2)
[BARO] I2C  50Hz ──┘                    │
                                        └→ PackedSensorData(86B)
                                             │ RPC [0xA5][TYPE][LEN][payload][XOR]
                                             ▼
                                        M4 수신·검증
                                          ├→ 링버퍼 → CSV → SD (100Hz 전량)
                                          └→ 4프레임마다 → XBEE (25Hz)
```

## 6.3 센서 데이터가 "유효"해지는 조건

각 센서는 **관문을 전부 통과해야만** 값이 반영되고 `xxxLastMs` 타임스탬프가 찍힌다.
하나라도 실패하면 **그 샘플 전체를 폐기**하고 이전 값이 그대로 남는다(부분 수용 없음).
부분 수용을 안 하는 이유: 같은 라인의 다른 필드도 검출 불가능하게 손상됐을 수 있고,
그걸 받아들이면 생존 판정까지 오염된다.

### IMU (`parsers::parseImuLine` → `imuSampleSane`)

| # | 관문 | 실패 시 |
|---|------|---------|
| 1 | `'\n'`까지 라인 조립, 버퍼 128B | 넘치면 버퍼 리셋 후 라인 폐기 |
| 2 | 첫 글자가 `*` | 라인 폐기 |
| 3 | 콤마가 **정확히 11개**(=12필드) | 라인 폐기 |
| 4 | 각 필드 `strtof` 성공(앞에 숫자 아닌 것 없음) + 구분자가 `,` 또는 `\0` | 라인 폐기 |
| 5 | 각 값 `isfinite` — `"nan"`/`"inf"`도 파싱되므로 명시 차단 | 라인 폐기 |
| 6 | `imuSampleSane()` 물리범위 | 라인 폐기 |

**5번이 필요한 이유**: NaN이 들어오면 이후 모든 비교가 거짓이 되어 조건이 **조용히
영원히 안 걸리고**, UKF 공분산이 영구 오염된다.

**6번 물리범위:**

| 항목 | 한계 | 근거 |
|------|------|------|
| roll / yaw | ≤ 180.5° | 데이터시트 출력범위 ±180 + 반올림 여유. 넓게 두면 오염된 `roll=360`이 `cos(360)=+1`로 **tilt 전개 조건을 관통**한다 |
| pitch | ≤ 90.5° | 데이터시트 출력범위 ±90 |
| gyro | ≤ 2200 dps | `ssg:5`=±2000 원시 출력 + 10% 여유 |
| accel | **≤ 30 g** | 아래 설명 |
| pos(9~11) | 검사 안 함 | 관성 드리프트가 수십 m까지 정상 |

> **accel이 왜 30g인가 (ssa:4는 ±16g인데)**
> `ssa:4`는 **원시 가속도계**의 풀스케일이다. 그런데 우리가 쓰는 `soa:3` 출력은
> 원시값이 아니라 **기체→글로벌 회전 + 중력 제거를 거친 계산값**이고, 그 결과는
> 다시 ±16으로 잘리지 않는다. 3축이 동시에 16g로 포화한 충돌은 크기가
> `√3 × 16 = 27.7g`이고 이게 한 글로벌 축에 거의 다 실릴 수 있으며, 중력 보정으로
> ±1g가 더해져 **약 28.7g까지 물리적으로 도달 가능**하다. 16으로 두면 **진짜 충돌
> 데이터를 폐기**하고, 연속 기각이 이어지면 거짓 `[WARN] IMU lost`까지 뜬다.
> 검출력 손실은 작다 — 이 검사가 잡는 오염은 소수점 유실(×10 이상)이라 실제 3g만
> 넘어도 여전히 30을 초과한다. 게다가 투표 창과 30ms 신선도 게이트가 이미 **단일
> 오염 라인을 무해화**하므로 이 검사는 더 이상 최후 방어선이 아니다.

이 함수는 **부팅 검사(`sensor_check`)와 런타임 파서가 공유**한다. 그래서
`[INIT] IMU OK`가 세는 라인과 비행 중 받아들이는 라인의 기준이 정확히 같다.

한 라인이 깨져도 사망이 아니다. 그 라인만 버리고 이전 스탬프가 살아 있으므로,
**500ms 동안 유효 라인이 하나도 없어야** 사망 판정이다.

### 바로미터 (`parseBaro`)

| # | 관문 | 실패 시 |
|---|------|---------|
| 1 | `readNonBlocking()` = DRDY 새 샘플 존재 | `false` 반환, 이전 고도 유지 |
| 2 | `isfinite(p)` && **300 ≤ p ≤ 1250 hPa** | 샘플 폐기 |
| 3 | 고도 환산 결과 `isfinite` | 샘플 폐기 |
| 4 | **변화율**: dt ≤ 200ms면 `\|alt − 직전수용alt\| ≤ 680 × dt(초)` | 샘플 폐기 |

**2번은 "칩이 살아있나" 수준**이다(고도로 −1,800 ~ +9,200m). 드라이버/버스 글리치가
0 hPa를 주면 +44,330m가 되어 고도 발사 투표를 0.5초에 채워버리므로 최소한 이건 막는다.
과거 `p>950` 필터는 **해발 550m 이상 발사장에서 전 샘플을 기각**해 기준기압이
1013으로 남는 지뢰였다 — 그래서 물리범위로 바꿨다.

**4번이 IMU 물리범위에 대응하는 진짜 타당성 검사**다. 680 m/s ≈ Mach 2 = 20ms당 13.6m.
일부러 헐겁게 잡았는데, **거짓 기각이 훨씬 위험한 방향**이기 때문이다 — 정상 데이터를
계속 자르면 500ms 뒤 바로미터가 사망 판정되어 고도 발사경로와 vz 전개경로가 둘 다
닫힌다. 진짜 글리치는 수백~수천 m라 이 정도로도 자릿수 차이로 걸린다.

기각된 샘플은 앵커(`prevValidAlt/Ms`)를 갱신하지 않으므로 **허용치가 스스로 커지고**,
dt가 200ms를 넘으면 판단을 포기하고 재앵커한다. 그래서 앵커가 잘못 잡혀도 기각이
무한히 이어지지 않는다(최대 200ms → 500ms 헬스 타임아웃 전에 복구).

통과하면 추가로:
- `altLaunchAvg` = **최근 실제 샘플 2개의 평균**. 루프가 아니라 **샘플 발생 시점**에만
  갱신한다 — 100Hz 루프에서 50Hz 값을 2개 평균내면 같은 값끼리 평균이라 무의미하고,
  4개를 평균내면 위상에 따라 결과가 달라진다. 샘플 소스에서 평균내면 위상 무관.
- `true` 반환 → **이때만 UKF 1스텝**([6.5](#65-ukf-왜-50hz인가))

### GNSS (`parsers::UbxPosllh` — NEO-M9N, UBX 바이너리)

모듈이 **UART1에서 NMEA를 끄고 UBX-NAV-POSLLH만 25Hz로 출력**하도록 설정돼 있다
(2026-08-04 u-center/VALGET 실측, Flash+BBR 저장 확인). 프레임:

```
[B5 62][01 02][1C 00][payload 28B][CK_A CK_B]   ← 36B × 25Hz ≈ 대역폭 23% @38400
```

| # | 관문 |
|---|------|
| 1 | 동기 바이트 `B5 62` |
| 2 | class/id = `01 02`(NAV-POSLLH), 길이 = 28 — 불일치는 재동기 |
| 3 | **Fletcher-8 체크섬**(class~payload) |
| 4 | **hAcc(수평정확도) ≤ 100m** — `GNSS_HACC_MAX_M` |
| 5 | 범위 \|lat\| ≤ 90, \|lon\| ≤ 180 |

**4번이 fix 판정을 대신한다** — POSLLH에는 fix 유효성 플래그가 없다. 대신 no-fix
프레임은 lat=lon=0에 **hAcc ≈ 4,294,967m**로 나오므로(호스트 재현 확인) hAcc 게이트가
자동으로 걸러낸다. 길이 기반 프레이밍이라 payload 안의 `B5 62`도 무해하다(재현 확인).

`gnssLastMs`는 **체크섬 유효 프레임이면** 찍힌다(hAcc 무관 — no-fix여도 수신기는
살아있는 것). 좌표는 hAcc 통과 시에만 갱신된다. GNSS는 **어떤 비행 판정에도 관여하지
않고** 기록·회수용이다.

구 NMEA 파서들(`parseNmeaLine` 등)은 펌웨어에서 더 이상 호출되지 않지만 parsers.h에
남겨뒀다 — 미사용 inline이라 플래시 비용 0이고, 호스트 테스트가 계속 커버하며, 모듈이
공장초기화되면(9600 NMEA로 복귀) 폴백 근거가 된다.

**모듈 쪽 설정도 비행 전 점검 대상이다.** 펌웨어는 아래 9개를 전제로 동작하며,
스크래치패드의 `m9n_verify_flight_cfg.py`가 Flash 레이어를 읽어 한 번에 대조한다
(불일치 시 exit 1): DYNMODEL=8, RATE-MEAS=40ms, UART1 38400/8N1,
POSLLH_UART1=1, UART1 OUT UBX=1·NMEA=0.

**DYNMODEL이 Airborne &lt;4g인 이유**: 구 설정 Portable은 **수직속도 상한이 50m/s**라
이 로켓의 상승속도(~100m/s 추정)에서 수신기 필터가 정상 측정치를 이상치로 버린다.
Airborne &lt;4g는 u-blox에서 가장 느슨한 모델로 **속도 타당성 검사 자체가 꺼진다**(고도만
검사, 상한 80km). 실측 최대 가속 10g는 모델의 4g 가정을 넘지만 이건 항법이 중단되는
하드 컷오프가 아니라 필터 예측이 뒤처지는 성능 저하이고, 더 느슨한 모델은 존재하지
않는다. 부스트 중 일시적 fix 상실은 수용한다 — **GNSS는 어떤 비행 판정에도 관여하지
않으므로** 하강 중 재획득만 되면 회수 목적은 달성된다.

## 6.4 신선도의 두 등급

같은 데이터에 목적이 다른 두 시계가 붙는다. **이 분리가 이 펌웨어에서 가장 중요한
안전 설계다.**

| | 판정용 (ctrl-fresh) | 헬스용 (alive) |
|---|---|---|
| IMU | **30ms** (3주기) | 500ms |
| 바로 | **60ms** (3주기) | 500ms |
| GNSS | — | 3000ms |
| 쓰는 곳 | **발사·전개 투표 4개, UKF 입력** | 로그, 캘리 스킵, **정적 착지 판정** |

**왜 나눴나.** 센서가 죽어도 `d.accel` 같은 값은 마지막 값이 그대로 남는다. 헬스
타임아웃(500ms)으로 투표를 막으면 **얼어붙은 값 하나가 50번 재투표**되어 어떤 창이든
채운다(가속 창은 190ms면 참). 실제 시나리오: 보드를 세게 치는 충격이 3g를 찍는
동시에 IMU 커넥터를 뽑으면, 그 마지막 3g가 190ms 동안 20표로 복제되어 **책상 위에서
LAUNCH가 뜬다.** 판정용을 30ms로 조이면 죽은 센서는 최대 4표에서 끊겨 20표를 못 채운다.

(정확히는 IMU 샘플 하나가 age 0/10/20/30ms로 **최대 4표**, 바로 샘플 하나가 최대 7표에
쓰인다. 핵심은 50표가 될 수 없다는 것.)

**정적 착지만 일부러 500ms 헬스를 쓴다.** 거기선 죽은 센서를 "잠잠"으로 쳐야 하고,
2500표 창에서 50표는 노이즈다.

`imuFreshNow()` / `baroFreshNow()` 두 함수가 투표·UKF·health 바이트의 **단일 기준**이라
셋이 어긋날 수 없다.

## 6.5 UKF — 왜 50Hz인가

`if (parseBaro(d)) parseKalman(d);` — **새 기압 샘플이 있을 때만** 필터를 돌린다.
이유가 두 개다.

1. MATLAB 생성 코드가 전파식에 **dt = 0.02s를 하드코딩**했고 프로세스 노이즈 Q도 같은
   dt로 만들어져 있다. 100Hz 루프에서 돌리면 실제 경과의 **두 배**를 적분한다.
2. 바로미터는 초당 50개만 새 값을 낸다. 100Hz로 돌리면 절반은 같은 고도를 다시 먹여
   한 측정을 이중 계산하고, 필터가 과신하게 된다(공분산이 실제 관측 1회당 두 번 축소).

생성 코드를 고치지 않고 **호출 주기를 센서에 맞추는 것**으로 둘 다 해결했다.
수정 전 실측: 정지 상태에서 `kf_vel = -0.926` 고정, `apogee = nan`. 수정 후: `kf_vel`
0 중심 ±0.3, apogee 정상값.

**"실제 주기가 정말 20ms인가"** — 필터가 타임스탬프를 안 쓰고 20ms를 가정하므로, 실제
간격이 다르면 속도가 그 비율만큼 편향된다(22ms면 \|vz\|가 10% 과대 → −7 임계가 실제
−6.4에서 걸림). 근거는 셋이다:

1. **드라이버가 명백한 부적합은 막는다(필요조건).** `bmp3_set_op_mode` →
   `validate_normal_mode_settings` → `verify_meas_time_and_odr_duration`이 측정시간
   (압력×8/온도×1 = 계산상 18.94ms)과 ODR 주기(50Hz = 20ms)를 비교해, 측정이 더 길면
   `BMP3_E_INVALID_ODR_OSR_SETTINGS`를 반환하고 `setupNormalMode`가 false가 된다.
   ⚠️ 다만 이건 **충분조건이 아니다** — 드라이버가 쓰는 건 계산상 전형값이고 데이터시트의
   변환시간 **최대는 21.53ms**(최소 측정률 46.42Hz)다. 통과했다고 모든 개체·조건에서
   정확히 50.00Hz라는 보장은 없다.
2. **폴링 지터는 편향이 아니다.** 루프는 10ms마다 폴링하므로 검출 간격은 10/20/30ms로
   흔들리지만 각 샘플은 정확히 한 번만 검출되므로 **평균 간격 = 센서 주기**다. 지터는
   필터 입력의 노이즈이지 스케일 오차가 아니다.
3. **런타임에서 재고, 그 결과가 vz를 무장·감시한다.** 비행 루프 시작 ~2초 뒤 깨끗한
   간격 100개(`CADENCE_ARM_N`)의 평균으로 `[ZERO] Baro cadence: ... OK`가 1회 나간다.
   **`vzCadenceOK`는 기본값이 false**라 그때까지 vz는 무장되지 않고, 평균이
   17.5~22.5ms(`CADENCE_MEAN_LO/HI_MS`) 밖이면 `vzTrusted`까지 내려가 **비행 내내
   vz가 꺼진다**(note `vz_off`).
   **빠른 방어는 롤링-4다**: 매 샘플, 최근 4개 깨끗한 간격의 합이 70~90ms(평균
   17.5~22.5)를 벗어나면 그 자리에서 vz를 500ms 블랭킹하고 투표창을 비운다. 4개인
   이유 — 기압 샘플 하나가 루프 ~3표로 복제되므로 실샘플 4개(~120ms)면 12표 창이
   찰 수 있어, **이보다 느린 감시는 투표와의 경주에서 진다**(과거의 "5연속 느린 간격"
   카운터는 20/30ms 교대 저하에서 매번 리셋돼 영원히 안 걸리는 구멍이 있었다 — 합
   검사는 교대 패턴도 sum=100으로 잡는다). 정상 위상 지터는 10과 30이 짝으로 나타나
   합이 ~80에 머물러 오탐하지 않고, 오탐해도 비용은 자가 복구되는 블랭킹뿐이다.
   무장 후에는 추가로 **50개 블록(`CADENCE_BLOCK_N`)마다 평균을 재확인**해 비행 중 계통적
   저하(예: 루프가 늘어져 실질 30ms cadence로 축퇴)가 생기면 같은 방식으로 영구
   차단한다 — 위상 지터(10/30ms 교대)는 평균이 20으로 유지되므로 오탐하지 않는다.
   임무 10초(`CADENCE_DEADLINE_MS`)까지 깨끗한 100개를 못 모으면(예: 40ms 주기 센서)
   `[WARN] insufficient clean samples`를 1회 남기고 fail-closed로 종료한다 — baro가
   아예 죽어 있으면 조용히 종료(이미 `Baro lost`가 보고됨). 미무장 구간은 PRELAUNCH
   한복판이라 무해하고, 그동안에도 가속 발사판정·tilt 백업·14초는 정상이다.

평균에는 **깨끗한 간격(≤35ms)만** 넣는다. 단발 누락(예: 60ms)까지 평균에 섞으면 100개 중
2개만으로 평균이 20.0 → 20.8로 밀려 **멀쩡한 센서의 vz를 영구 차단**해버린다(호스트 실측).
계통적 rate 오차는 이 평균이, 단발 누락은 아래 6.7의 건별 판정이 담당한다 — 역할 분리.

⚠️ 기준기압 수집 로그(`[BARO] t=`)의 간격은 **이 판정에 쓰면 안 된다.** 그 루프는
`delay(20)` + 샘플마다 RPC 로그라서 구조적으로 50Hz를 넘을 수 없다 — 센서가 아니라
그 루프를 측정한 값이다(6초 273샘플 = 45.5Hz가 나오는 이유).

운용 한계 하나: apogee 회귀의 시간 입력(`micros()` 기반)은 **부팅 후 71.6분에 래핑**
된다. 전개 판단에는 미사용이지만, apogee 값이 필요하면 부팅 후 71분 내에 발사할 것
(15분 운용 규칙에 이미 포함되는 조건).

**입력 변환:**
```
accel_z_in = (IMU가 30ms 이내면 d.accel[2], 아니면 0) × 9.81 + 9.81
```
- `× 9.81` : g → m/s²
- `+ 9.81` : 모델이 **비력(specific force)** 을 기대하고 내부에서 9.81을 빼는데,
  `soa3`는 이미 중력이 제거된 선형가속도다. `a_비력 = a_선형 + g`는 편법이 아니라 항등식.
- **낡으면 0** : 얼어붙은 가속도를 계속 적분하면 속도가 폭주한다(동결 −8g면 0.2초 만에
  `vz < −7` = 오전개). 선형가속도 0 = "등속" 가정 = 바로미터 측정에만 의존하는 안전한 축퇴.

**부호**: 글로벌 +Z = 위(ENU). 들어올려 유지하는 테스트에서 IMU 자체 거리 `pos_z`가
+0.583m로 계단 변화한 것으로 확정했다.

## 6.6 투표 창 (VoteWin)

"최근 N표 중 need표 이상이 참이면 발동"하는 비트마스크 링버퍼. 이진 투표라서:

- 스파이크 하나가 평균을 끌어올릴 수 없다 (평균 방식의 약점 해소)
- 몇 표 흔들려도 진행이 리셋되지 않는다 (연속-지속 방식의 약점 해소)

| 창 | N / need | 유효 확인시간 | 용도 |
|---|---|---|---|
| `vwAccel` | 20 / 12 | ~120ms | 발사 가속도 (모터 진동으로 8표 흔들려도 통과) |
| `vwAlt` | 40 / 24 | ~240ms | 발사 고도 |
| `vwVz` | 12 / 7 | ~70ms | 전개 낙하속도 |
| `vwTilt` | 25 / 15 | ~150ms | 전개 기울기 |
| `vwStatic` | 2500 / 1500 | ~15s | 정적 착지 (노이즈 1000표 허용) |

전부 **60% 기준**이다(2026-08-04 통일. vz만 7/12 = 58.3% — 12×0.6=7.2가 정수가 아니고
7이 8보다 60%에 훨씬 가깝다). 기압 기반 조건은 값이 두 번씩 들어가지만 **비율 검사라
중복에 편향되지 않는다.**

`VoteWin`은 **비트 링과 카운트만** 가진다 — 시각을 일절 기억하지 않는다. 예전엔 첫 참표
시각(`riseMs`)을 들고 발사시각을 소급보정했으나 **2026-08-08에 보정과 함께 제거**했다
([6.7](#67-상태-전이) LAUNCH 항목).

## 6.7 상태 전이

```
STARTUP ──(부팅 완료)──> PRELAUNCH ──> LAUNCH ──> DEPLOY ──> LANDED
  0xBA        0xBA                     0xBB       0xBC       0xBD
```
상태 바이트 값은 지상국 `STATE_MAP`과 고정 약속이므로 **변경 금지**.

### STARTUP → PRELAUNCH (부팅 ~37초)

서보 자체점검 3s → (IMU 살아있으면) 자이로+지자기 캘리 21s → (바로 살아있으면)
기준기압 6s → PRELAUNCH.

**죽은 센서는 캘리를 건너뛴다** — 얼어붙은 값 위에서 영점을 잡지 않기 위함이고,
덤으로 IMU가 죽었을 때 21초를 아낀다.

**기준기압 품질 게이트** — 아래 4개를 **모두** 만족해야 기압 기반 두 경로가 켜진다:

```
normal 모드 진입 성공  AND  샘플 ≥ 200  AND  reject ≤ 20  AND  변동 ≤ 0.5 hPa
       ↓ 합격                                    ↓ 불합격
baroRefValid = true                    baroRefValid = false  AND  vzTrusted = false
(고도 발사경로 + vz 전개경로)            (가속 발사 + tilt + 14초만 남음)
```

정상 실측은 273샘플 / reject 0 / 변동 0.03~0.04 hPa이므로 여유가 크다. 0.5 hPa는 약 4m로,
강풍이나 이동 중 부팅은 확실히 걸러진다.

**게이트 하나가 두 경로를 함께 관장하는 이유**: `reject>20`은 물리범위 밖 샘플이 6초에
20개 이상 나온 것 = 오작동 센서이고, `spread>0.5`는 가만히 있는데 4m를 배회한 것 = 강풍이거나
노이즈 센서다. 그런 센서의 **미분값(속도)** 을 낙하산 트리거로 쓰는 건 절대 고도를 쓰는 것보다
오히려 더 위험하다. 잃는 것은 그 조건에서의 vz 경로뿐이고 tilt와 14초 타이머는 그대로다.

두 발사감지 경로가 모두 없으면 `[ERROR] NO LAUNCH DETECTION PATH`.

### PRELAUNCH → LAUNCH — 두 경로 OR

| 경로 | 조건 | 투표 |
|------|------|------|
| **가속도** | `IMU 30ms 이내` && `\|accel_z\| > 2g` | 20표 중 12표 (**≈120ms**) |
| **고도** | `baroRefValid` && `바로 60ms 이내` && `altLaunchAvg > 10m` | 40표 중 24표 (**≈240ms**) |

IMU가 죽어도 고도가, 바로가 죽어도 가속도가 감지한다.
`accel_z`는 `soa3`라 중력이 빠져 있으므로 "순수 가속 2g"이고 **장착 방향과 무관**하다.

**`Launch_Time`은 감지 시각 그 자체다 — 소급보정하지 않는다** (2026-08-08 팀 결정).

```cpp
Launch_Time = (uint32_t)s.time;   // 보정 없음
```

투표가 차는 데 걸리는 시간(가속 ~120ms / 고도 ~240ms)만큼 **실제 이륙보다 늦은 값**이고,
그만큼 하위 타이머가 전부 뒤로 밀린다:

| 타이머 | 실제 이륙 기준 실효값 |
|--------|----------------------|
| tilt 5초 잠금 | 5.12초(가속 감지) / 5.24초(고도 감지) |
| 강제 14초 | 14.12초 / 14.24초 |

**왜 보정을 버렸나.** 이전 구현은 투표창의 첫 참표 시각(`riseMs`)에서 경과분을 빼서
이륙 시각을 되짚었는데, 그 정의에 함정이 있었다 — 산발적인 참표가 창 길이보다 촘촘히
이어지면 `count`가 0으로 안 떨어져 **riseMs가 부팅 직후 값에 영원히 고정**되고, 그
상태로 발사가 감지되면 `Launch_Time`이 부팅 시점이 되어 **다음 루프에서 14초 조건이 즉시
참** — 점화 직후 추력 최대 구간에서 사출된다. 그래서 `maxHeld` 클램프(창 길이 상한)와
언더플로 클램프를 덧대야 했다. 보정 자체를 없애면 **이 고장군 전체와 클램프 두 개가
함께 사라진다.** 대가는 위 표의 0.1~0.2초 지연뿐이고(14초 대비 1% 미만), 지연 방향은
전개를 **늦추는** 쪽이라 오사출 위험을 키우지 않는다. `VoteWin`에서 `riseMs` 필드와
`update()`의 `now` 인자도 함께 제거해, 투표창은 이제 시각을 아예 다루지 않는다.

### LAUNCH → DEPLOY — 전개 사다리 (vz → tilt → 14초)

기압 공백은 **두 지점에서** 감시한다. 감시하는 대상이 다르기 때문이다.

| 어디서 | 무엇을 보나 | 동작 |
|--------|------------|------|
| `runDecision` (LAUNCH, 매 루프) | 마지막 샘플의 **나이** `now - baroLastMs` | >60ms면 블랭킹 500ms, >200ms면 `vzTrusted=false` |
| **`parseBaro` (샘플 수용 시)** | 직전 샘플과의 **간격** `dt` | >35ms면 블랭킹 500ms(상태 무관), LAUNCH 중 >200ms면 `vzTrusted=false` |

**둘 다 필요한 이유** — `runDecision`은 "공백이 *진행 중*"만 알 수 있다. 공백이 *끝나는*
순간에는 같은 루프에서 `parseBaro`가 이미 `baroLastMs`를 갱신해버렸으므로 나이가 0으로
읽혀 **공백이 있었다는 사실 자체가 사라진다.** 그런데 UKF는 방금 그 공백 전체를 20ms 한
스텝으로 처리해서 속도 전이를 만들어놓은 뒤다.

`runDecision`만으로 못 잡는 경우가 실제로 둘 있다:

- **M7 루프 자체가 멈춘 경우**(RPC 블로킹 등) — 공백 동안 `runDecision`이 아예 안 돌아
  블랭킹이 쌓이지 않는다. 복구 루프에서는 이미 fresh라 라치도 안 걸린다.
- **PRELAUNCH 중 공백이 점화 직전 복구** — 위 표의 첫 행은 `case LAUNCH` 안에만 있어서
  PRELAUNCH 공백은 블랭킹을 만들지 않는다.

호스트 재현(`scratchpad/audit_gap.cpp`)에서 300ms·800ms 루프 정지 시 **간격 판정 없이는
라치가 걸리지 않고 블랭킹도 없음**을, 추가 후에는 둘 다 정상 동작함을 확인했다. 정상
스트림(10/20/30ms 지터)에서 거짓 블랭킹은 0이다.

`BARO_STEP_MAX_MS = 35`의 근거: 10ms 폴링 × 50Hz 센서는 위상차로 **10/20/30ms가 정상**
이고 30이 정상 최대다. 40ms부터는 샘플 누락이므로 35가 그 사이에 있고 루프 지터도 흡수한다.
거짓 양성 비용은 vz 500ms 블랭킹(자동 복구)뿐이라 여유를 두는 쪽이 옳다.

**왜 둘 다 필요한가.** UKF는 새 기압 샘플에만 스텝하고 항상 0.02초를 전파하므로,
공백 후 첫 샘플이 **공백 전체의 고도 변화를 한 번의 20ms 스텝으로** 처리한다 → 속도
전이. 실측 거동: 실제 −5 m/s로 하강 중 180ms 공백이 나면 추정치가 6샘플 동안 −7 m/s
아래로 흔들려 12표 창을 채울 수 있다. 블랭킹은 그 전이를 흘려보내되 **경로는 살린다**.
영구 차단은 "센서가 고장났다"고 부를 만큼 긴 공백에만 쓴다 — vz는 주 정점검출 경로이고
tilt와 14초는 백업일 뿐이라, 60ms 딸꾹질 하나에 버리면 안 된다.

전개는 사다리다(2026-08-07 재구성). **관성 센서 없이 만들어진 속도값으로는 낙하산을
열지 않는다**는 팀 결정에 따라, vz 경로는 IMU와 바로미터가 **둘 다** 건강할 때만
열린다. 루프마다 정확히 한 경로만 투표하고 나머지 경로의 표는 리셋되며, 강제 타이머는
센서 상태와 무관하게 항상 평가되는 최후 백업이다.

| 경로 | 활성 조건 | 판정 조건 | 투표 |
|------|-----------|-----------|------|
| **1. 낙하속도(vz)** | `baroRefValid && baroAlive && vzTrusted` — IMU 사망은 아래 라치가 `vzTrusted`를 내리므로 자동 포함 | **5초 락 해제** && `vzUsableNow()` && `kf_vel < −7 m/s` | 12표 중 7표 |
| **2. 기울기 백업** | vz 경로 비활성 && `imuAlive`(500ms) — **기압 상태는 안 봄** | **5초 락 해제** && `IMU 30ms 이내` && `cos(roll)·cos(pitch) > 0.70711` | 25표 중 15표 |
| **3. 강제 타이머** | 항상 | **5초 락 해제** && `발사 후 14초` (14>5라 오늘은 무동작 — 미래의 타이머 단축이 잠금 약속을 깨는 것 방지) | 투표 없음 |

**IMU 사망 라치.** LAUNCH 중 `imuAlive`(500ms)가 꺼지는 순간 `vzTrusted=false`로
**영구** 차단한다(`[WARN] vz deploy path disabled (IMU dead in flight)`, note
`vz_off`). 기압 공백 라치와 같은 편도 라치이고, 같은 이유로 **LAUNCH에서만**
발동한다 — 패드 정비 중 커넥터 흔들림이 그 비행의 주경로를 미리 태우면 안 된다
(발사 순간 이미 죽어 있으면 첫 루프에서 즉시 발동). 영구인 이유: 이 팀의 최다 반복
하드웨어 고장이 IMU 커넥터 접촉 불량인데 접촉 불량은 죽살이를 반복하므로, 자동
복귀는 vz 권한이 비행 중 계속 붙었다 떨어지는 상태를 만든다. **한 번 죽은 센서는
주경로에 다시 앉히지 않는다** — 복구된 IMU는 기울기 백업으로만 돌아온다.

`vzUsableNow()` = trusted && cadence OK && **IMU 30ms 이내** && 기압 60ms 이내 &&
`isfinite` && |vz| < 200 && 블랭킹 해제 — **7항 AND**. IMU가 죽진 않았지만 값이 낡은
30~500ms 구간에는 vz 투표가 일시 정지되고(note `vz_settle`), UKF가 가속도 0으로
절름거리는 동안의 추정치는 표가 되지 못한다. 짧은 공백은 신선해지면 자동 재개된다.
단, 5초 전개 잠금 해제 후 `vzUsableNow()`가 **1000ms 연속 거짓**이면
`vzTrusted=false`로 영구 차단하여 tilt 백업에 권한을 넘긴다. 40ms 주기처럼
cadence 통계에서 제외되는 지속 저하 및 비유한 속도도 이 감시가 처리한다.
중간에 usable이 참이면 연속 시간은 리셋된다. 복구 후에도 영구 차단은 유지한다.

과거의 **상승(+3m/s 연속 10루프) 확인 무장 항은 2026-08-08에 제거**했다(팀 결정).
발사 직후 구간은 5초 락이 대신 지킨다. 대가: "상승을 한 번도 안 만드는 하강-고정
기압 고장"(포트 누설류 — 부팅 품질검사·cadence는 통과할 수 있다)이 이전엔 vz를 영원히
못 열었지만 이제 **5.07초에 연다**(호스트 재현 — 이전 force 14초 → 이후 vz 5.06초).
부수 효과: 패드에서 조건이 모두 정상이면 health 0x80이 켜져 note가 `ok`로 찍힌다
(이전엔 발사 전이라 항상 `vz_settle`).

센서 조합별 결과(비행 중):

| 기압 | IMU | 전개 수단 |
|------|-----|----------|
| 정상 | 정상 | **vz** + 14초 |
| 정상 | 사망 | **14초만** — 기압 단독 vz 금지(팀 결정 2026-08-07) |
| 문제 | 정상 | **tilt** + 14초 |
| 문제 | 사망 | **14초만** |

`kf_vel`은 속도 벡터 크기가 아니라 UKF의 1D 수직속도다. UKF 입력은 글로벌 Z축
가속도(`accel_z_in`)와 기압고도뿐이고, 출력 `kf_velocity_out`이 `kalman[1]`에 들어간다.
부호는 글로벌 +Z가 위쪽이므로 하강은 음수, 전개 조건은 `kf_vel < −7 m/s`다.

**기울기가 방향코사인인 이유.** 회전행렬의 3열(기체 Z축의 월드 표현)과 연직 벡터의
내적이 `cos(roll)·cos(pitch)`다. 그래서:

- **yaw가 소거**된다 — 중력축 회전(스핀)은 기울기를 바꾸지 않으므로 당연하다
- pitch=±90 짐벌 구간에서도 곱이 **연속**이다 (개별 각이 요동쳐도 무관)
- **모든 낙하 방향에서 기하가 동일**하다

값: 기수 위 = −1, 발사대 캔트(roll 178°) = −0.996, 수평 = 0, **+0.7071 = 기수가
지면 아래 45°**. 구버전의 `|roll|<45 || |pitch|>135` 조건은 후자가 **영원히 거짓인
죽은 절**이었다(EBIMU pitch 범위가 ±90이라 135를 넘을 수 없음).

**5초 잠금(`DEPLOY_LOCKOUT_MS`)은 세 경로 전부에 걸린다**(2026-08-08 확장 — 이전엔
tilt만 잠그고 "vz는 상승 중 어차피 거짓"이라는 근거로 열어뒀다). 발사 후 5초 동안은
어떤 전개 조건이 참이어도 투표 입력이 false라 표가 쌓이지 않고, 5.00초에 빈 창에서
시작한다 — 최단 전개는 vz 5.07초 / tilt 5.15초(호스트 재현). 목적: 연소 중 돌풍·스핀
(tilt)과 천음속 압력 포트 과도(vz)에 의한 오사출 방지 — 상승 확인이 제거된 지금은
발사 직후 구간을 지키는 **유일한** 가드다. 대가: 모터 조기 소진으로 5초 전에 낙하가
시작되는 비정상 비행에서 전개가 5.07초로 밀린다 — 지연이지 상실이 아니다(락 해제 후
조건이 여전히 참이면 즉시 발화, 호스트 재현 S3). 정점 ~10초인 정상 비행에서는
아무것도 바뀌지 않는다.

`imuCtrlFresh` 게이트가 없으면 부팅 시 죽은 IMU의 euler가 0으로 굳어 `cos(0)·cos(0) = +1`
이 되어 **T+5초에 무조건 발동**한다. 게이트가 필수인 이유.

### DEPLOY → LANDED — 정적 판정 단독

**서보 열림(0°)이 상태 전환·로그보다 먼저 실행된다.** 세 전개 경로 모두 `enterDeploy()`를
거치는데, 그 안의 순서가 `Parachute.write(SERVO_OPEN_DEG=0)` → 상태 변경 → `logMsg`다.
`logMsg`는 RPC로 나가고 **RPC 쓰기는 블로킹**이므로([6.10](#610-m4-내부)), 통신이 안전 동작보다
앞서면 안 된다. 서보 기하는 기체 실측(2026-08-08): **0° = 낙하산 개방, 120° = 잠금**
(`SERVO_OPEN_DEG`/`SERVO_CLOSE_DEG` — 각도는 반드시 이 상수로만 쓸 것).
(예전에는 상태만 바꾸고 로그를 보낸 뒤 *다음 루프*에서 서보를 움직였다.)

이후 **열림 유지 1000ms → 착지 검사 → (아니면) 닫힘 500ms
→ 다시 열림** 반복. 이 닫았다 여는 사이클은 **낙하산이 걸렸을 때를 위한 재시도이며
의도된 동작**이다(팀 결정, 버그 아님).

"열기 먼저"인 이유: 예전엔 닫기 500ms로 시작해서 첫 전개가 0.5초(≈4~5m 낙하) 늦었다.

착지 검사는 **서보가 열린 시점(phase 1)에서만** 수행 → LANDED는 항상 낙하산이 열린
상태로 끝난다.

```
moving = IMU살아있음 && (자이로 3축 중 하나라도 > 5 dps  또는  가속 3축 중 하나라도 > 0.2 g)

고도가 앵커에서 ±2m 벗어나면 → 앵커 재설정 + 창 하드 리셋 (투표 아님)

staticLanded = (!moving)가 2500표 중 1500표 ≈ 15초 (최근 25초 창 안에서)
```

**고도 이탈만 투표가 아니라 하드 리셋인 이유**: 바로 노이즈는 ±0.25m라 착지한 로켓은
±2m 밴드를 절대 안 벗어난다(8σ). 반대로 IMU가 조용한 완만한 하강에서는 **고도 변화가
유일한 운동 증거**인데, 이걸 40:1로 희석하면 공중에서 착지 판정이 날 수 있다.

기준값 근거: 정지 시 실측 자이로 ~0.2 dps, `soa3` 가속 ~0.04 g.

**센서 사망 시 자동 축퇴**:
- IMU 죽음 → `moving=false`. 얼어붙은 큰 자이로값이 착지를 영원히 막는 걸 방지.
  여기만 `imuAlive`(500ms)를 쓰는 것은 **의도적**이다 — 낡은 데이터는 "잠잠"으로 읽혀야 한다.
- 바로 죽음 → 고도 동결 → 밴드 이탈 없음
- 둘 다 죽음 → 순수 ~20초 타이머. 판단 근거가 하나도 없을 때 할 수 있는 게 없고
  서보는 어차피 열린 채로 끝난다(팀 수용). 대가는 아직 하강 중이어도 재시도가 멈추는 것.

과거의 `|alt|<2m` 빠른 경로는 삭제했다 — 완만한 하강 중 패드 고도 밴드를 지나가면
공중에서 만족될 수 있었고, 애초에 착지점이 패드 ±2m 안일 때만 동작했다.

## 6.10 M4 내부

**IPC 수신 상태머신** — `[0xA5][TYPE][LEN_L][LEN_H][payload][CHECK]`를 바이트 단위로
조립한다. 상태 0~5, 마지막 5에서 **XOR 체크섬을 검증한 뒤에만** dispatch한다.

체크섬이 필요한 이유: M4 수신은 rpmsg 콜백이 **512B RingBuffer**에 넣는 구조인데,
`store_char`는 가득 차면 **바이트를 조용히 버린다**(덮어쓰기 아님). 100Hz×91B=9100 B/s
이므로 **M4 메인 루프가 ~56ms 이상 멈추면** 프레임 중간이 잘린다. 그러면 상태머신이
payload 상태에 남아 **다음 프레임의 헤더를 데이터로 흡수**하고, 바이트 수가 LEN에
도달하는 순간 **두 프레임을 이어붙인 버퍼**를 dispatch한다. 길이만 보는 검사는 이걸
정상으로 받아들였다 — 그 쓰레기가 CSV 행이 되고 XBEE로 나갔으며, **state 바이트가
payload 0번**이라 지상국에 엉뚱한 비행 상태가 뜰 수도 있었다.

호스트 재현(1·7·20·60바이트 유실):
```
체크섬 전: 5개 dispatch, 그 중 오염 1개  ← 정상으로 통과함
체크섬 후: 4개 dispatch, 오염 0개, 거부 1개, 이후 재동기 정상
정상 스트림 6프레임: 양쪽 다 6개 전달, 거짓 거부 0
```
비행 안전에는 영향이 없다(M4는 제어 권한이 0이고 M7으로 아무것도 돌려보내지 않는다).
데이터 무결성 문제다.

**링버퍼와 우선순위** — `sdRing`은 88B×512 ≈ 44KB로 100Hz 기준 약 5초의 여유다.
CSV 변환은 라이터 스레드가 하므로 링은 작게 유지된다. 링이 가득 차면 새 프레임을
버리고 `sdDrops`를 센다. 로그 링은 48칸으로, 기준기압 측정 중 `[BARO]` 버스트(~50Hz)가
유실 없이 들어가는 크기다.

**xbeeLog는 메인(loop) 문맥에서만 호출해야 한다.** 라이터 스레드에서 부르면 텔레메트리
프레임 바이트 사이에 끼어들어 XBEE 스트림이 깨진다. 그래서 라이터는 플래그
(`g_sdFailReport`)만 세우고 실제 송신은 loop가 한다. 같은 패턴을 `g_ipcBadReport`,
`g_landedReport`에도 쓴다.

**M7 쪽 같은 함정**: `ipcSend` 안에서 `logMsg`를 부르면 `logMsg → ipcSend → logMsg`로
재귀한다. 그래서 RPC 경고도 플래그(`g_rpcWarn`)로 넘기고 loop에서 발행하며,
**플래그를 logMsg보다 먼저 지운다**(logMsg가 ipcSend를 다시 타면서 세운 결과가
지워지지 않도록).

**RPC 쓰기는 블로킹이다.** `RPC.write()` → `rpmsg_send()`는 OpenAMP의 **블로킹 변형**
으로 빈 tx 버퍼를 기다린다(non-blocking은 `rpmsg_trysend`). 그래서 M4가 멈추면 이
호출이 늘어져 100Hz 루프와 서보 FSM까지 끌 수 있고, 그걸 측정해서 `[WARN]`을 낸다.
반환값 검사는 **의미 없다** — `RPCClass::write()`는 `OPENAMP_send`의 결과를 버리고
무조건 `len`을 돌려주므로 short write는 관측 자체가 불가능하다.

**세션 로테이션** — 부팅마다 `.csv`/`.bin`/`.txt`가 모두 없는 첫 인덱스를 찾아
`flight_NNN`을 만든다. 기존 파일은 절대 건드리지 않는다(`.bin`도 확인하는 것은 구
바이너리 포맷 세션과의 충돌 방지).

## 6.11 지우면 사고 나는 것들

코드에 `// !`로 표시해둔 자리들. 전부 위에 근거가 있다.

| 위치 | 지우면 |
|------|--------|
| `imuFreshNow()` (UKF 입력) | IMU 사망 시 동결 가속도 적분 → 0.2초 만에 거짓 전개 |
| 투표 4곳의 ctrl-fresh 게이트 | 얼어붙은 값이 재투표되어 거짓 LAUNCH/DEPLOY |
| `if (parseBaro(d)) parseKalman(d)` | UKF가 실제 경과의 2배를 적분 + 측정 이중계산 |
| 고도 밴드 이탈의 **하드 리셋** | 완만한 하강 중 공중에서 LANDED |
| 정적 판정의 `imuAlive` (ctrl-fresh 아님) | 낡은 데이터가 "운동 중"으로 읽혀 착지 판정 불가 |
| IPC 체크섬 검증(state 5) | 이어붙인 쓰레기 프레임이 정상 데이터로 기록됨 |
| `enterDeploy()`의 서보-먼저 순서 | 블로킹 RPC 로그가 낙하산 명령보다 앞서게 됨 |
| 경고를 `logEvent`로만 발행(직접 logMsg 금지) | 판정 전 경로에 블로킹 RPC가 되살아남 — 새 경고를 추가할 때도 반드시 logEvent |
| cadence 롤링 블록의 무조건 카운터 리셋 | 차단 후 카운터가 무한 증가 |
| vz 투표의 `isfinite(vz)` | 필터가 −Inf로 발산하면 전개 조건이 참이 됨 |
| `parseBaro`의 dt 기반 공백 판정 | 끝난 공백이 보이지 않게 됨 — 루프 정지·PRELAUNCH 공백 후 전이가 그대로 투표에 들어감 |
| cadence 평균에서 아웃라이어 제외 | 단발 누락 2개가 평균을 밀어 멀쩡한 센서의 vz를 영구 차단 |
| `ipcSend`의 링 push(블로킹 write 금지) | M4 정지가 곧 비행제어 정지가 됨 — 루프에서 `RPC.write` 직접 호출 금지 |
| CLOSE 시 `servoReopenGuard.attach` | 루프가 CLOSE 직후 죽으면 낙하산이 닫힌 채 고착 |
| LANDED의 `staticLanded && !moving` | 20초 이력만으로, 지금 움직이는 중에도 착지 선언 가능(~5초 창) |
| 롤링-4 cadence 합 검사(매 샘플) | 20/30ms 교대 저하가 감시를 우회한 채 vz 투표(~100ms)가 먼저 참 |
| USB 출력의 txThread 배치 | 루프에 블로킹 가능 IO가 되살아남 — 루프에서 `Serial.print` 직접 호출 금지 |
| PRELAUNCH 공백 시 `vwAlt.reset()` | 재획득 과도값이 공백 전 투표에 올라타 고도 발사 성립 |
| `g_rpcWarn`을 logMsg **전에** 클리어 | 재귀로 경고가 사라지거나 중복 발행 |
| `sdWriter`가 BelowNormal인 것 | SD 쓰기 중 RPC 수신이 멈춰 100Hz 무손실이 깨짐 |
| M7 `+ 9.81` (UKF 입력) | 비력 대신 선형가속도가 들어가 속도 추정이 통째로 틀어짐 |

| `[WARN] Baro cadence: ... -> vz deploy path disabled` | 실측 평균이 17.5~22.5ms 밖. vz가 비행 내내 꺼진다(tilt+14초는 정상). 압력 오버샘플링을 ×8→×4로 낮추고 재측정할 것 |

| `[WARN] Baro cadence: insufficient clean samples` | 10초 내 깨끗한 간격 100개 미달(센서가 40ms 주기 등). vz 미무장으로 종료 |
| `vz deploy path disabled (baro gap NNNms)` | 비행 중 기압 샘플 간격이 200ms 초과. 커넥터/전원 점검 |
| `IPC frame rejected (checksum)` | M4 루프가 56ms 이상 멈춰 코어간 바이트 유실. 해당 프레임만 버려짐 |
| `RPC link: slow=..us dropped=N evdrop=N` | txThread가 본 느린 쓰기 / 링 넘침으로 버린 프레임 / 이벤트 큐 넘침. M4·링크 점검 — **비행 루프는 이것과 무관하게 계속 돈다** |

| XBEE 수신이 띄엄띄엄 | 링크 간헐성(채널 간섭/근접 포화). 25Hz 초과 송신은 유실 정상 |
| 지상국에 apogee가 NaN | 바로미터 미연결 상태로 비행 루프가 돈 것 — baro 복구하면 정상 |

## 코드 수정 시 지켜야 할 것

- **업로드 순서 M4 → M7**, Flash 오프셋 변경 금지.
- 상태 바이트(0xBA~0xBD)와 `PackedSensorData` 크기(86B)는 지상국과의 약속이다.
  구조체를 바꾸면 `static_assert`가 빌드를 막는다 — 그때는 지상국 파서도 같이 고칠 것.
- `lib/Adafruit_BMP3XX-master`는 수정본(`setupNormalMode()`/`readNonBlocking()` 추가).
  원본 라이브러리로 교체하면 100Hz 루프가 깨진다.
- M4에서 변수명 `logf` 사용 금지(C 수학함수와 충돌), `#include <unistd.h>` 금지(`sleep()` 충돌).
- Serial1(XBEE)은 M4 전용 — M7 코드에서 만지지 말 것.
- 임계값을 조일 때는 **거짓 기각의 대가**를 먼저 따질 것. 이 펌웨어에서는 대부분
  "못 잡는 것"보다 "정상 데이터를 버리는 것"이 더 위험하다([6.3](#63-센서-데이터가-유효해지는-조건) 참조).
